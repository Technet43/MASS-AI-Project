# Real-Data Requirements

This document distinguishes synthetic testing, controlled proxies, public benchmarks, and field validation for MASS-AI.

## Validation levels

| Level | Data source | Meaning |
| --- | --- | --- |
| L0 | Synthetic data generated by MassAIEngine | Useful for demos, regression tests, and controlled feature behavior. It is not evidence of field performance. |
| L1 | SGCC-style realistic proxy generated by real_data.py | Useful for a controlled domain-shift rehearsal. It is generated data, not real-world validation. |
| L2 | Properly documented public real dataset | An academic-style benchmark when source, license, preprocessing, and split policy are recorded. It is not Turkish field validation. |
| L3 | Turkish distribution-company or municipality pilot data | Partner-specific validation, subject to permission, privacy, and operator review. |
| L4 | Live monitored deployment | Evidence for operational impact only after monitored outcomes and governance are in place. |

The committed evidence in this repository is L1. The input adapter can accept a compatible real CSV, but that capability alone does not establish L2, L3, or L4.

## Minimum dataset fields

For a useful L2 or L3 evaluation, request:

- a stable anonymous meter or customer identifier;
- at least 90 daily readings per entity; 180 or more days is preferred;
- a confirmed inspection outcome, theft label, or clear anomaly label when supervised metrics are reported;
- region, tariff, feeder, transformer, or meter metadata when available;
- an inspection or event date when lead time is evaluated.

## Compatibility fields are not observed fields

SGCC-style daily inputs commonly omit hourly, network, and operational information. The current adapter can populate neutral or generated compatibility values so the existing pipeline can run. This is useful for integration checks, but not for final performance claims.

Do not use compatibility values for the following fields as if they were observed data:

- tamper_event_count
- days_since_last_tamper
- meter_age_years
- temperature_sensitivity
- solar_relief_factor
- night_day_ratio when only daily totals exist
- transformer_loss_pct when no transformer hierarchy exists

When a source does not provide these inputs, the evaluation must disclose that fact and either exclude the fields, run an ablation, or explicitly label the result as an integration test.

## Required benchmark record

Every L2 or L3 evaluation should record:

- source, license or permission, date range, row count, and label rate;
- preprocessing, missing-value handling, feature availability, and proxy-derived fields;
- train/test split policy, including customer, time, feeder, or transformer leakage controls;
- ROC-AUC, PR-AUC, precision, recall, F1, calibration, and the confusion matrix at an agreed threshold;
- inspection-capacity assumptions and precision/recall at that capacity;
- segment results where reliable metadata exists.

## Acceptance gates

Before describing the prototype as suitable for a data pilot:

- L2 or L3 data access and evaluation scope are documented.
- The final feature set does not silently rely on unavailable synthetic or proxy-derived fields.
- Thresholds are tied to a stated review capacity.
- The command, configuration, and report are reproducible.

Before discussing production deployment:

- A partner has reviewed a real-data pilot and its error profile.
- Privacy, retention, access control, monitoring, and incident-response responsibilities are agreed.
- Drift monitoring, retraining approval, and human review workflows are documented and tested.

See [model validation](MODEL_VALIDATION.md) for the metric policy.
