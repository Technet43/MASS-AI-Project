# Real Data Requirements

This document defines what counts as real validation for MASS-AI and separates it from proxy or synthetic testing.

## Validation Levels

| Level | Data source | Status meaning |
|---|---|---|
| L0 | Synthetic data generated by `MassAIEngine` | Useful for demos, regression tests, and controlled feature behavior. Not proof of field performance. |
| L1 | SGCC-style realistic proxy generated by `real_data.py` | Useful for domain-shift rehearsal. Still not real-world validation. |
| L2 | Public real benchmark dataset such as SGCC | Acceptable academic-style benchmark if license and preprocessing are documented. |
| L3 | Turkish DSO or municipality pilot data | Required before claiming production readiness for the Turkish market. |
| L4 | Live monitored deployment | Required before claiming operational loss-reduction impact. |

The current repository reaches L1 by default and can run L2 when a valid SGCC-style CSV is supplied.

## Minimum Dataset Fields

For a useful L2/L3 benchmark, the input should include:

- Stable customer or meter identifier.
- At least 90 daily consumption readings per customer. 180+ days is preferred.
- Theft, fraud, inspection, or confirmed anomaly label if supervised metrics are reported.
- Meter region, tariff, feeder, or transformer metadata when available.
- Inspection date or event date when evaluating lead time.

## Fields That Must Not Be Invented For Final Claims

The current SGCC adapter can generate neutral or random proxy values for missing operational fields so the existing model pipeline can run. These are acceptable for compatibility tests only.

Do not use proxy-generated versions of these fields for final business or academic claims:

- `tamper_event_count`
- `days_since_last_tamper`
- `meter_age_years`
- `temperature_sensitivity`
- `solar_relief_factor`
- `night_day_ratio` when only daily totals are available
- `transformer_loss_pct` if no transformer hierarchy exists

If these fields are unavailable in real data, the benchmark report must say so and either exclude them from the production feature set or run an ablation test.

## Required Benchmark Outputs

Every serious benchmark should report:

- Dataset source, date range, row count, theft/anomaly rate, and preprocessing decisions.
- Train/test split policy, including whether customers, transformers, or time windows leak across splits.
- ROC-AUC, PR-AUC, precision, recall, F1, and confusion matrix at the chosen operating threshold.
- False positive cost estimate and investigation capacity assumption.
- Segment-level results by region, tariff, and customer type when metadata exists.
- Calibration or score distribution plot.

## Acceptance Gates

Before a pilot claim:

- L2 benchmark completed on public real data or L3 private data.
- No synthetic/proxy-only features used in the final model without clear labeling.
- Precision and recall reported at a threshold chosen for inspection capacity.
- Reproducible command and report committed under `reports/`.

Before a production claim:

- L3 pilot completed with partner feedback.
- Drift monitoring and retraining policy documented.
- Data privacy, retention, and access-control policy approved by the partner.
- Human review workflow tested with field operators.
